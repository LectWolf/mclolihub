# 分组健康与 API 密钥路由设计

**日期：** 2026-08-20
**状态：** 已实现
**范围：** 分组主动探测、故障恢复、用户侧状态展示、API 密钥多分组路由

## 目标

管理员可以在分组上直接开启主动探测并配置探测模型。系统记录分组可用性、首字延迟和历史趋势，并在用户侧展示倍率、状态、真实用户延迟、6 小时可用率等信息。API 密钥支持固定分组、低价优先、响应优先和用户自定义顺序四种方式，并允许用户设置最大倍率及候选分组限制。

## 已确认规则

### 多账号探测

1. 每个启用探测的分组按账号既有优先级顺序执行探测。
2. 探测账号排序沿用 `account_groups.priority`、账号优先级和稳定 ID 顺序，不另建一套排序含义。
3. 第一个成功账号使本轮探测立即结束，分组保持或恢复可用。
4. 账号运行状态分为 `active`、`probing`、`unavailable` 和 `balance_insufficient`；没有健康记录的新账号默认可用。
5. 用户请求确认上游故障后，账号立即进入探察期；即时探测成功恢复 `active`，失败后依次进入 30 秒、60 秒、120 秒和 300 秒恢复探测。
6. 恢复探测连续失败超过 300 秒阶段后进入 `unavailable`，不再无限重复 300 秒；只有下一次 10 分钟常规分组探测可以恢复它。
7. 常规探测按分组内账号原顺序检查 `active`、`probing`、`unavailable` 账号，首个成功即停止；常规失败只记录事件，不推进探察期步进。
8. 分组只有在至少存在一个 `active` 且可调度账号时可用；所有账号处于探察期、不可用或余额不足时分组不可用。
9. 恢复探测成功会恢复该账号并重新计算分组健康；余额不足只能由管理员手动恢复。

主动探测轮次全失败会更新分组健康为不可用；真实用户请求中的单个或多个上游错误只更新对应账号，不直接把分组写成失败。真实请求导致全部账号都不可调度时，分组仅派生为“无健康账号”，供用户展示和动态候选过滤使用。

### 分组健康门控

分组健康门控只影响多分组动态路由：低价优先、响应优先和自定义顺序。固定单分组路由完全保留现有账号调度行为，不因探测失败、探测过期或无探测记录而切换或拒绝该分组；固定分组仍受用户设置的最大倍率限制，也仍受现有账号禁用、凭据、额度和可调度规则约束。

探测未开启时，分组显示“未启用探测”，并继续作为动态路由候选，不以“未知”状态阻断流量。探测开启后，动态路由候选应满足：

```text
分组处于 active
请求模型和协议受支持
至少存在一个可调度账号
分组健康状态不是显式不可用或余额不足
```

没有探测记录或探测未启用时默认可用；只有显式状态才阻断动态路由。分组健康由账号集合派生：只要至少一个账号健康，分组就可用；所有账号都处于探察期、不可用或余额不足状态时，分组没有可调度账号并从动态路由候选中移除。

### 账号错误和余额不足

`401/403`、模型错误、`429`、上游 `5xx`、网络失败和超时等均先进入现有账号失败处理，不直接把分组设置为失败。具体冷却、凭据刷新、限流窗口和恢复方式继续沿用对应平台的账号规则。

上游明确返回余额不足、额度耗尽或 credit exhausted 时，必须与用户自身钱包余额不足区分：

1. 将上游账号标记为独立的“余额不足”状态并从调度中排除。
2. 账号管理页使用蓝色“余额不足”状态展示原因和发生时间。
3. 余额不足状态由管理员手动恢复；在管理员恢复前，不因为后续自动探测成功而自动恢复账号。
4. 分组没有健康账号，且不可用账号集合中包含余额不足账号时，用户侧分组状态优先显示“余额不足”；若全部只是普通失败，则显示“不可用”。

余额不足确定为独立于现有 `active/inactive/error` 生命周期字段的运行状态。账号管理页将其显示为蓝色状态标签并提供管理员恢复动作；普通探测成功不能自动清除余额不足状态，也不能误报为用户自身余额不足。

### 分组探测配置

探测在分组内配置，至少包含启用开关、探测模型和正常探测间隔。正常探测间隔允许管理员配置在 30 秒到 1 小时之间，默认 10 分钟；模型由管理员按分组选择，典型配置为 `gpt-5.6-sol`。

OpenAI 分组优先使用 Responses API 发起低 token 探测，并使用流式响应记录探测 TTFT。探测请求必须标记为内部探测，不计入用户自身使用量和真实用户性能样本；上游实际产生的费用仍属于运营成本，不能假定提供方不会计费。

### 低价优先

低价优先按当前用户对分组的实际生效倍率从低到高排序，而不是按上游账号成本、探测费用或历史消费排序。先移除用户对该 API 密钥禁用的分组，再应用最大倍率过滤；相同倍率时依次按分组健康质量、管理员分组排序和分组 ID 保证结果稳定。

后续若要改为“同模型实际价格优先”，应作为新的路由方式实现，不能静默改变“低价优先”的含义。

### 响应优先

探测 TTFT 与真实用户 TTFT 属于不同数据域，不能放在同一排行榜直接比较。响应优先采用以下规则：

1. 对存在真实用户成功请求样本的候选分组，按最近窗口分组整体真实用户 TTFT 排序，不区分请求模型。
2. 当前不设置最低样本门槛；一个有效样本也允许参与，但界面必须同时显示样本数，使低置信度可见。
3. 只要至少一个候选分组有真实用户样本，无样本分组就排在所有有样本分组之后，不能凭更低的探测 TTFT 抢占首位。
4. 只有当全部候选分组都没有真实用户样本时，才回退使用探测 TTFT 排序。
5. 路由比较最近 6 小时成功请求的滚动 P50，避免平均值被少量极慢请求放大；页面同时展示平均值、P95 和样本数。
6. 缺少真实用户 TTFT 且缺少探测 TTFT 的分组排在最后，再按稳定排序兜底。

真实用户性能窗口确定为最近 6 小时，并合并同一分组内全部模型的成功请求。只有确实收到首个 token 的真实请求进入 TTFT 样本；主动探测、用户参数错误、客户端主动取消以及没有首 token 概念的端点不进入排序指标。后续可在配置中扩展，但路由和页面必须使用同一窗口口径。

### 自定义顺序

用户从自己有权限的分组中为 API 密钥添加候选分组并拖拽排序。没有添加的分组自然不参与，因此自定义顺序模式不再提供单独的“禁用分组”列表。运行时先应用最大倍率、模型能力、账号可调度性和分组健康门控，再从剩余候选中选择用户顺序最靠前的分组。用户排序不能绕过权限、倍率上限、模型能力或健康门控。

### API 密钥候选控制

所有路由模式都允许用户设置可选的最大倍率：

- `fixed`：固定分组超过最大倍率时直接拒绝请求，不自动换组；它只绕过探测健康门控，不绕过倍率上限。
- `cheapest`：从用户有权限、未禁用且不超过最大倍率的健康分组中选择最低倍率。
- `fastest`：候选过滤与低价优先相同，但排序使用真实用户 TTFT。
- `custom`：只使用用户显式添加并排序的分组，不提供额外禁用列表，仍应用最大倍率。

最大倍率比较当前用户的实际生效倍率，包括用户专属分组倍率；未设置最大倍率表示不限制。低价优先和响应优先的“禁用分组”只影响当前 API 密钥，不改变分组本身状态，也不影响用户的其他 API 密钥。

动态 API 密钥的协议平台由 `route_platform` 决定：`openai` 只进入 Responses、Chat Completions 等原生 OpenAI 处理路径，`anthropic` 只进入 Messages 路径，`grok` 只进入 Grok 路径。旧的 `auto` 密钥继续沿用其绑定分组的平台，避免跨协议候选混用。动态候选每次请求实时读取当前 active 分组，因此管理员新增更便宜分组后，不需要重新编辑 API 密钥，下一次请求即可参与排序。

### 动态路由故障转移

低价优先、响应优先和自定义顺序采用跨分组故障转移：

1. 请求开始时排除已被探测标记失败的分组和账号，再按当前模式形成有序候选分组列表。
2. 从第一个候选分组选择一个当前可用账号；账号选择继续使用现有分组内调度规则。
3. 若该账号成功，本次路由结束。
4. 若该账号出现错误分类器认定的可重试上游失败，本次请求不尝试同一分组的第二个账号，直接选择下一个候选分组的一个可用账号。
5. 按候选分组顺序一直尝试到成功或最后一个候选分组耗尽，并受请求整体截止时间约束。
6. 失败账号立即进入“待验证探测”状态并从新请求候选中排除。独立探测成功则恢复账号；探测仍失败则启动 30 秒、60 秒、120 秒和 300 秒恢复节奏。
7. 同一账号同时被多个真实请求发现失败时，只创建一个验证/恢复任务，防止重复探测。
8. 某个账号真实请求失败不直接标记整个分组失败；同组其他健康账号可以承接后续新请求，但不再参与当前请求。

即时验证探测有每账号 2 分钟限频，并且异步执行，不阻塞当前用户请求：真实请求首次发现账号失败时可以后台触发一次验证探测；同一账号在此前 2 分钟内已经触发过即时验证，则只记录失败并交给既有探测/恢复任务，不再次发起即时探测。该限频用于避免账号在“刚恢复、立即失败”的边界上反复触发探测。

不可重试的用户参数错误、内容策略拒绝和客户端主动取消不跨分组重试。上游账号余额不足时标记账号余额不足并跨到下一候选分组，但不为该账号启动自动恢复探测；它由管理员恢复。

流式响应沿用现有端点行为：只有在上游尚未写出语义内容、响应尚未对用户产生不可逆输出时才允许切换账号或分组。一旦已经写出首个 token、消息事件或其他语义响应，禁止重新发起请求，直接按原协议结束当前流并记录错误：Responses 使用协议要求的失败终止事件，其他 SSE 使用错误事件，普通非流请求直接返回原有错误响应。

固定单分组模式不使用跨分组故障转移，继续执行现有固定分组内的账号处理逻辑。

## 状态与数据

建议将低频配置与高频状态分开：

- `groups` 保存探测开关、探测模型和常规探测间隔等配置。
- `group_health_states` 保存每个分组的当前健康快照、最近成功、失败计数、下一次恢复时间和状态原因。
- `group_health_events` 保存主动探测及影响健康的真实请求结果，用于审计和趋势聚合。
- `api_keys.route_mode` 保存 `fixed`、`cheapest`、`fastest` 或 `custom`。
- `api_keys.max_rate_multiplier` 保存该密钥可接受的最大生效倍率；空值表示不限制。
- `api_key_group_preferences` 在低价/响应模式保存用户排除项，在自定义模式保存显式候选和顺序。

现有 `api_keys.group_id` 继续承载固定分组模式，保证升级后所有旧密钥行为不变。

## 探测和真实流量指标

主动探测指标：

- 探测状态与错误类别
- 探测 TTFT
- 探测总耗时
- 探测账号
- 最近成功时间
- 6 小时探测可用率

真实用户指标：

- 成功请求 TTFT P50、平均值和 P95
- 样本数
- 总响应耗时
- 非用户参数错误率
- 缓存命中率
- 6 小时真实请求可用率

两组指标分别存储、分别展示。探测数据只负责健康判断和无真实样本时的排序回退，真实用户数据负责响应优先排序。

用户侧时间条建议按 5 分钟聚合，最近 6 小时共 72 个桶：绿色为成功，黄色为降级或高延迟，红色为失败，灰色为无数据。探测趋势和真实用户趋势需要使用不同图例。

## 运行时流程

```text
API 密钥请求
  -> 应用 API 密钥最大倍率
  -> fixed: 直接使用原 group_id，绕过分组健康门控；超倍率则拒绝
  -> cheapest/fastest/custom: 取得该密钥允许的候选分组
       -> 按模式应用禁用列表或用户自定义候选
       -> 过滤最大倍率、权限、模型能力、探测失败账号和账号可调度性
       -> 过滤探测已开启但健康不合格的分组
       -> 应用倍率、真实用户 TTFT 或用户顺序排序
       -> 每个分组使用现有调度器选择一个账号
       -> 可重试失败时标记账号待验证，当前请求直接进入下一分组
       -> 失败账号由独立探测验证，仍失败则进入恢复节奏
       -> 记录请求结果，但不阻塞用户响应
```

主动探测应复用现有账号请求适配和模型映射能力，但分组健康需要保持独立模块，不能要求管理员重复填写渠道监控的 Endpoint 和 API Key。

## 开发顺序

1. 固化账号运行状态、错误分类和分组级跨模型统计口径。
2. 增加数据库迁移、领域类型与仓储。
3. 实现分组健康状态机和串行探测轮次。
4. 实现账号独立恢复调度及多实例防重复探测。
5. 将真实请求结果接入健康事件和 6 小时聚合。
6. 在多分组路由前接入健康门控，保持固定分组路径不变。
7. 实现 `cheapest`、`fastest` 和 `custom` 路由解析。
8. 增加管理员分组探测配置。
9. 增加用户侧分组状态和 API 密钥路由配置。
10. 补充迁移兼容、状态机、错误分类、并发调度、路由稳定性和前端交互测试。

每一步完成并验证后再进入下一步，不把状态机、路由和前端一次性混成单个大改动。

## 已实现边界与运行约束

1. 首期跨分组动态故障转移只启用于文本推理端点：`/v1/messages`、`/v1/chat/completions` 和 `/v1/responses`。图片、视频、批处理等可能产生上游副作用的端点不自动重放；固定分组路由继续沿用各端点原有行为。
2. 多实例部署通过扫描、分组和账号级 leader lock/租约避免重复探测；即时验证探测仍受每账号 10 分钟限频约束。
3. 管理员恢复上游账号余额不足是显式健康恢复事件，写入 `group_health_events.kind=admin_recovery`，不会伪装成主动探测或真实用户请求样本。

## 非目标

- 不用探测 TTFT 覆盖或修正真实用户 TTFT。
- 不让固定分组 API 密钥因健康门控自动切换到其他分组。
- 不把单个账号失败直接等同于整个分组失败。
- 不把上游账号余额不足误报为用户自身余额不足。
- 不在本功能中改变现有分组内账号负载均衡和计费规则。
